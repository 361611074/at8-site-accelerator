## 1. 产品与方案

### 1.1 Product

```
product_id: at8-site-accelerator-pro
name:       AT8 Site Accelerator Pro
```

一个产品挂多个 Plan。Product 与 License 的 `product_id` 必须一致
（`LICENSE_SPEC.md` §8 更新接口的校验项之一）。

### 1.2 Plan（建议，需确认）

| Plan | 席位 | 周期 | 建议价 | 说明 |
| --- | --- | --- | --- | --- |
| `single` | 1 | 年付 | **$49 / 年** | 个人站长 |
| `team` | 5 | 年付 | **$99 / 年** | 小团队 / 多站 |
| `agency` | 不限 | 年付 | **$199 / 年** | 建站服务商 |
| `lifetime-single` | 1 | 一次性 | **$149** | 含 1 年更新，之后可续更新 |

字段：

```
Plan {
  id, product_id, slug, name,
  seats_total,            // null 表示不限
  billing_period,         // year | once
  price_usd, price_cny,   // 分为单位存储，避免浮点
  active, sort_order
}
```

**金额一律用整数"分"存储**，展示时才格式化。这是支付与对账的基本纪律，
浮点数算钱迟早出事故。

### 1.3 区域定价（§110）

- 基准价以 **USD** 存储；
- 按账单国家/地区展示 **CNY** 价格（人民币价格**单独维护**，不做实时汇率换算——
  实时汇率会让同一商品在不同时间显示不同价格，引发客诉）；
- 区域判定依据：账单地址 > 支付渠道返回的地区 > IP（仅作兜底，不作为记账依据）。

## 2. 领域模型

```
User ──< Order ──< OrderItem >── Plan >── Product
 │          │
 │          └──< Invoice
 │          └──< Payment
 │
 └──< License ──< Site
 └──< DownloadToken

Coupon ──< CouponRedemption >── Order
```

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| `User` | id, email, password_hash, name, country, created_at | 邮箱唯一；登录失败限流 |
| `Order` | id, user_id, status, total, currency, plan_id, period | 见 §3 状态机 |
| `OrderItem` | order_id, plan_id, seats, unit_price, quantity | 一单通常一项，预留多项 |
| `Invoice` | id, order_id, number, issued_at, pdf_path | 发票号**不可变**，重发不换号 |
| `Payment` | id, order_id, gateway, gateway_txn_id, amount, status | `gateway_txn_id` 唯一，用于幂等 |
| `License` | 见 `LICENSE_SPEC.md` §1 | 订单支付成功后生成 |
| `DownloadToken` | id, license_id, expires_at, used_at | 短期签名，§26 禁止永久链接 |

## 3. 订单状态机

```
                 ┌──────────┐
                 │  draft   │  结账页初始化
                 └────┬─────┘
                      │ 提交
                      ▼
                 ┌──────────┐
                 │ pending  │  已创建，等待支付渠道回调
                 └────┬─────┘
          ┌───────────┼───────────┐
          ▼           ▼           ▼
     ┌────────┐  ┌─────────┐  ┌──────────┐
     │  paid  │  │ failed  │  │ cancelled│  超时 / 用户放弃
     └───┬────┘  └────┬────┘  └──────────┘
         │            └──► 可回到 pending（重试支付）
         ▼
   ┌───────────┐
   │ fulfilled │  生成 License + 发邮件 + 开放下载
   └─────┬─────┘
         │ 退款
         ▼
   ┌───────────┐
   │ refunded  │  同时触发 License revoke
   └───────────┘
```

**状态转换规则**（必须严格执行，否则对账会乱）：

1. `pending → paid` **只能由支付回调触发**，前端跳转**不得**直接置为 paid；
2. `paid → fulfilled` 是**系统动作**，成功后才发 license 邮件；
3. 任何状态转换**必须写审计日志**（谁、何时、从什么到什么、依据哪个 webhook 事件 ID）；
4. `refunded` **不可回到** `paid`；如需继续服务，必须新建订单。

## 4. 结账流程

```
1. 选择 Plan
2. 登录 / 注册（或游客结账后补账号）
3. 填账单信息（国家决定币种与税）
4. 选支付渠道（见 PAYMENT_SPEC.md 区域推荐）
5. 跳转到渠道收银台 / 拉起 SDK
6. 渠道异步回调 → 验签 → 幂等处理 → paid → fulfilled
7. 展示成功页 + 发 license 邮件（含下载链接与激活说明）
```

**关键约束**：

- 成功页**不得**依赖回调完成后才展示（回调可能延迟）——先展示"支付处理中"，
  再由前端轮询订单状态；
- 回调失败/超时必须提供**手动对账入口**：用 `gateway_txn_id` 在渠道后台查证后手动置 paid；
- 结账页**不收集**与履约无关的个人信息（遵循 Free 版"不收集数据"的产品承诺）。

## 5. 发票与税务

- 发票号格式：`AT8-YYYYMMDD-<sequence>`，**一经生成不可修改**；
- 作废用**红冲发票**（负数金额），不修改原发票；
- 税率与税号展示由区域规则决定；**税务合规主体未确定前（Q4 相关），
  发票模块只做"形式发票（proforma）"，不开具正式税务发票**。

> 这条是刻意的保守设计：在主体资质与税务登记确定前开正式发票是合规风险。

## 6. 优惠券

```
Coupon {
  code,                 // 大写，唯一
  type,                 // percent | fixed
  value,                // percent: 0-100；fixed: 分
  max_redemptions,      // null = 不限
  redeemed_count,
  applies_to_plans[],   // 空 = 全部
  starts_at, expires_at,
  active
}
```

**校验顺序**（顺序错了会给出误导性错误）：

1. 存在且 active；
2. 在有效期内；
3. 未超出 `max_redemptions`；
4. 适用于当前 Plan；
5. 计算折扣（结果**不得低于 0**，且不低于渠道最小收款额）。

## 7. 下载交付（§26）

- **禁止**公开永久下载链接；
- 每次下载生成**短期签名 URL**（≤ 15 分钟），或一次性 token；
- 下载响应必须带 `sha256`，供客户端（`LICENSE_SPEC.md` §7.2）校验；
- 下载行为记入审计日志（谁、何时、哪个版本、哪个 IP）。

## 8. Customer Center（§99）

| 页面 | 内容 |
| --- | --- |
| Account | 基本信息、邮箱、密码、国家 |
| Orders | 订单列表 + 详情 + 发票下载 |
| Licenses | license key、已激活站点、席位使用情况、解绑（对应 §20 Site Management） |

| Invoices | 发票列表与 PDF |

**取消订阅**必须：

- 明确告知"取消后将在到期日停止续费，当前周期内仍可正常使用"；
- **不做**诱导挽留的暗黑模式（如把"继续订阅"做得比"取消"更显眼）；
- 到期后按 `LICENSE_SPEC.md` §6 的宽限逻辑处理，**不立即吊销**。

## 9. 客户数据隔离（§117）

用户只能看到**自己的**订单、License、下载、发票。

**必须实现并测试的防线**：

| 风险 | 防线 | 测试 |
| --- | --- | --- |
| **IDOR** | 所有资源查询强制带 `user_id` 过滤（在 ORM 层做，不靠控制器自觉） | 用 A 账号请求 B 账号的 order_id / license_id / invoice_id，期望 404（**不是 403**，403 会泄露"资源存在"） |
| **权限提升** | 角色校验在服务端，不信任任何前端传参 | 普通用户调用管理员接口，期望 403 |
| 枚举泄露 | 资源 ID 用不可猜测值（UUID 或带校验位） | 遍历 ID 不应命中他人资源 |
| 越权下载 | 下载 token 绑定 `license_id`，校验归属 | 用他人 token 下载，期望 404 |

> **404 而非 403**：对未授权资源返回 404 可以避免确认"该 ID 确实存在"，
> 这是 IDOR 防护的常规做法。

## 10. 管理后台角色（§118）

| 角色 | 权限 |
| --- | --- |
| Super Admin | 全部 |
| Support | 查看订单/ License / 用户，**可解绑站点、重发 license 邮件**；**不可**退款、不可改价 |
| Finance | 订单、退款、发票、对账；**不可**解绑站点 |
| Developer | 只读 + 日志/接口调试；**不可**触碰用户数据与金额 |

所有敏感操作（退款、吊销、改价、解绑）**必须写审计日志**并支持追溯。
