# 性能基准方案

> 对应开发计划书 §65（性能目标）、§88（基准测试）。
>
> **诚实声明**：本文件是**测量方案与验收标准**，不是测量结果。
> 真实基准必须在目标站点、目标主机、真实流量下测量才有意义——
> 在开发机上跑出来的数字对用户毫无参考价值。当前环境不具备该条件，
> 因此这里只定义"怎么测、测什么、达到什么算合格"，不编造数字。

---

## 一、要证明的核心命题

本插件的核心卖点是**精准失效**，所以基准测试必须能证明这件事：

> 编辑一篇文章时，被清除的缓存页面数应显著小于整站页面总数。

如果测不出这个差异，那"精准失效"就只是营销词。

## 二、测量环境要求

| 项目 | 要求 |
| --- | --- |
| 站点 | 内容 ≥ 500 篇、分类 ≥ 20 个、有分页的 WordPress 站 |
| 主题 | 使用真实主题（不要用 twentytwentyfour 这种极简主题，测不出渲染成本） |
| 插件 | 保留用户真实使用的插件集（Elementor / WooCommerce 等） |
| 主机 | 与用户实际环境同级（共享主机就测共享主机） |
| 缓存 | 测量前清空所有缓存层（页面缓存、对象缓存、OPcache、CDN） |
| 工具 | `ab` 或 `wrk`（压测）、`curl -w`（单次 TTFB）、Query Monitor（查询数） |

## 三、测量项与验收标准

### 3.1 缓存命中率

```bash
# 预热
for i in $(seq 1 50); do curl -s -o /dev/null "https://example.com/page-$i/"; done

# 抽样 200 个 URL，统计响应头
for i in $(seq 1 200); do
  curl -s -I "https://example.com/page-$i/" | grep -i '^X-AT8-Cache:'
done | sort | uniq -c
```

**验收**：`HIT` 占比 ≥ 95%（排除登录态、预览、表单页等本就该绕过的请求）。

### 3.2 TTFB（首字节时间）

| 场景 | 测量方法 | 验收标准 |
| --- | --- | --- |
| 缓存 HIT | `curl -w '%{time_starttransfer}'`，取 20 次中位数 | 相比未启用插件时**降低 ≥ 60%** |
| 缓存 MISS | 同上 | 相比未启用插件时**不劣化超过 10%** |

MISS 不劣化是关键：优化模块（压缩、懒加载）都在 MISS 路径上，
如果 MISS 慢了 50%，那说明优化本身的开销吃掉了缓存的收益。

### 3.3 数据库查询数

用 Query Monitor 查看单页查询数：

| 场景 | 验收标准 |
| --- | --- |
| 缓存 HIT | **0 次查询**（drop-in 命中时 WordPress 完全没启动） |
| 缓存 MISS | 与未启用插件时相比，增量 ≤ 2 次（一次读配置、一次读设置） |

### 3.4 精准失效（核心命题）

```bash
# 1. 记录缓存文件总数
find wp-content/cache/at8-site-accelerator -name 'index.html' | wc -l

# 2. 通过 WP-CLI 编辑一篇文章（触发 save_post）
wp post update 123 --post_title="benchmark test"

# 3. 再次统计
find wp-content/cache/at8-site-accelerator -name 'index.html' | wc -l
```

| 场景 | 验收标准 |
| --- | --- |
| 编辑 1 篇文章（500 篇站） | 被清除的页面数 **≤ 15 个**（文章本身 + 首页 + 归档 + 分类 + 标签 + 作者 + 翻页） |
| 对比：`purge_scope=all` | 全部清除（作为对照，证明差异确实来自策略而非别的因素） |

> 若站点有 500 篇文章，精准失效应该只影响个位数百分比。
> 这是本插件相对"整站清空"类插件的核心价值，必须能量化。

### 3.5 并发下的稳定性

```bash
ab -n 5000 -c 100 https://example.com/
```

| 指标 | 验收标准 |
| --- | --- |
| 失败请求 | 0 |
| 平均响应时间 | 与 `-c 1` 时相比增长 ≤ 2 倍 |
| 缓存目录文件数 | 无重复写入产生的 `.tmp` 残留 |

> `.tmp` 残留检查很重要：`Filesystem::put_contents()` 用临时文件 + `rename`，
> 若 `rename` 失败且清理逻辑有问题，会在缓存目录里堆积垃圾。

### 3.6 前端指标（Lighthouse / PageSpeed Insights）

| 指标 | 启用前 | 启用后 | 验收标准 |
| --- | --- | --- | --- |
| LCP | 基线 | — | **不劣化**（懒加载首屏提权就是为了这个） |
| CLS | 基线 | — | 不劣化 |
| TBT | 基线 | — | 改善（前端精简 + 懒加载） |
| 总传输体积 | 基线 | — | 降低 ≥ 10%（HTML 压缩 + 资源精简） |

> LCP **不劣化**比"变好"更重要。懒加载最常见的自伤方式就是把首屏大图也标成 lazy，
> 直接恶化 LCP。本插件前两张图强制 `eager` 就是为了避免这个。

### 3.7 Redis vs 磁盘

同一站点分别在 `cache_backend=disk` 与 `cache_backend=redis` 下测 TTFB：

| 后端 | 预期 |
| --- | --- |
| 磁盘 | 本地 SSD 上通常已经足够快 |
| Redis | 在"缓存目录位于网络存储（NFS / 云盘）"时优势明显 |

**验收**：Redis 模式的 TTFB 不劣于磁盘模式（若劣于，说明 Redis 连接开销大于收益，
应在文档中建议这类站点使用磁盘模式）。

### 3.8 内存与进程

| 指标 | 验收标准 |
| --- | --- |
| 单请求峰值内存 | 相比未启用插件时增量 ≤ 4MB |
| drop-in 命中时的内存占用 | ≤ 2MB（它只读一个配置文件和一个缓存文件） |

## 四、必须记录的对照基线

每次基准测试必须同时记录三个配置的结果，缺一个就无法解释差异来源：

| 配置 | 说明 |
| --- | --- |
| **A. 无插件** | 原始 WordPress |
| **B. 仅页面缓存** | 只开 ①，其余全关 |
| **C. 全功能** | 全部模块开启 |

- B − A = 页面缓存的收益
- C − B = 优化模块的净收益（若为负，说明某个优化模块在拖后腿，需要定位）

---

## 五、已知会干扰结果的因素

测量时必须排除或记录：

1. **CDN**：CDN 命中时请求根本到不了源站，TTFB 数据无意义。测量时绕过 CDN 或直接打源站 IP。
2. **OPcache 冷启动**：第一次请求会编译 PHP，必须预热后再测。
3. **对象缓存**：Redis Object Cache 会掩盖数据库查询差异，测"查询数"时应单独关闭。
4. **共享主机邻居**：同一台机器上的其他站点会影响结果，应在低峰期测量并记录时间。
5. **HTTP/2 / HTTP/3**：多路复用会影响并发测试结果，记录协议版本。
6. **插件自身的后台任务**：数据库清理定时任务若正好在测量期间运行会污染数据。
