# 性能基准方案

> 对应开发计划书 §65（性能目标）、§88（基准测试）。
>
> **诚实声明**：本文件是**测量方案与验收标准**，不是测量结果。
> 真实基准必须在目标站点、目标主机、真实流量下测量才有意义——
> 在开发机上跑出来的数字对用户毫无参考价值。当前环境不具备该条件，
> 因此这里只定义"怎么测、测什么、达到什么算合格"，不编造数字。

---

## 一、要证明的核心命题

本插件的核心卖点是**精准失效**，所以基准测试必须能证明这件事：

> 编辑一篇文章时，被清除的缓存页面数应显著小于整站页面总数。

如果测不出这个差异，那"精准失效"就只是营销词。

## 二、测量环境要求

| 项目 | 要求 |
| --- | --- |
| 站点 | 内容 ≥ 500 篇、分类 ≥ 20 个、有分页的 WordPress 站 |
| 主题 | 使用真实主题（不要用 twentytwentyfour 这种极简主题，测不出渲染成本） |

| 缓存 | 测量前清空所有缓存层（页面缓存、对象缓存、OPcache、CDN） |
| 工具 | `ab` 或 `wrk`（压测）、`curl -w`（单次 TTFB）、Query Monitor（查询数） |

## 三、测量项与验收标准

### 3.1 缓存命中率

```bash
# 预热
for i in $(seq 1 50); do curl -s -o /dev/null "https://example.com/page-$i/"; done

# 抽样 200 个 URL，统计响应头
for i in $(seq 1 200); do
  curl -s -I "https://example.com/page-$i/" | grep -i '^X-AT8-Cache:'
done | sort | uniq -c
```

**验收**：`HIT` 占比 ≥ 95%（排除登录态、预览、表单页等本就该绕过的请求）。

### 3.2 TTFB（首字节时间）

| 场景 | 测量方法 | 验收标准 |
| --- | --- | --- |
| 缓存 HIT | `curl -w '%{time_starttransfer}'`，取 20 次中位数 | 相比未启用插件时**降低 ≥ 60%** |
| 缓存 MISS | 同上 | 相比未启用插件时**不劣化超过 10%** |

MISS 不劣化是关键：优化模块（压缩、懒加载）都在 MISS 路径上，
如果 MISS 慢了 50%，那说明优化本身的开销吃掉了缓存的收益。

### 3.3 数据库查询数

用 Query Monitor 查看单页查询数：

| 场景 | 验收标准 |
| --- | --- |
| 缓存 HIT | **0 次查询**（drop-in 命中时 WordPress 完全没启动） |
| 缓存 MISS | 与未启用插件时相比，增量 ≤ 2 次（一次读配置、一次读设置） |

### 3.4 精准失效（核心命题）

```bash
# 1. 记录缓存文件总数
find wp-content/cache/at8-site-accelerator -name 'index.html' | wc -l

# 2. 通过 WP-CLI 编辑一篇文章（触发 save_post）
wp post update 123 --post_title="benchmark test"

# 3. 再次统计
find wp-content/cache/at8-site-accelerator -name 'index.html' | wc -l
```

| 场景 | 验收标准 |
| --- | --- |
| 编辑 1 篇文章（500 篇站） | 被清除的页面数 **≤ 15 个**（文章本身 + 首页 + 归档 + 分类 + 标签 + 作者 + 翻页） |
| 对比：`purge_scope=all` | 全部清除（作为对照，证明差异确实来自策略而非别的因素） |

> 若站点有 500 篇文章，精准失效应该只影响个位数百分比。
> 这是本插件相对"整站清空"类插件的核心价值，必须能量化。

### 3.5 并发下的稳定性

```bash
ab -n 5000 -c 100 https://example.com/
```

| 指标 | 验收标准 |
| --- | --- |
| 失败请求 | 0 |
| 平均响应时间 | 与 `-c 1` 时相比增长 ≤ 2 倍 |
| 缓存目录文件数 | 无重复写入产生的 `.tmp` 残留 |

> `.tmp` 残留检查很重要：`Filesystem::put_contents()` 用临时文件 + `rename`，
> 若 `rename` 失败且清理逻辑有问题，会在缓存目录里堆积垃圾。

### 3.6 前端指标（Lighthouse / PageSpeed Insights）

| 指标 | 启用前 | 启用后 | 验收标准 |
| --- | --- | --- | --- |
| LCP | 基线 | — | **不劣化**（懒加载首屏提权就是为了这个） |
| CLS | 基线 | — | 不劣化 |
| TBT | 基线 | — | 改善（前端精简 + 懒加载） |
| 总传输体积 | 基线 | — | 降低 ≥ 10%（HTML 压缩 + 资源精简） |

> LCP **不劣化**比"变好"更重要。懒加载最常见的自伤方式就是把首屏大图也标成 lazy，
> 直接恶化 LCP。本插件前两张图强制 `eager` 就是为了避免这个。

### 3.7 Redis vs 磁盘

同一站点分别在 `cache_backend=disk` 与 `cache_backend=redis` 下测 TTFB：

| 后端 | 预期 |
| --- | --- |
| 磁盘 | 本地 SSD 上通常已经足够快 |
| Redis | 在"缓存目录位于网络存储（NFS / 云盘）"时优势明显 |

**验收**：Redis 模式的 TTFB 不劣于磁盘模式（若劣于，说明 Redis 连接开销大于收益，
应在文档中建议这类站点使用磁盘模式）。

### 3.8 内存与进程

| 指标 | 验收标准 |
| --- | --- |
| 单请求峰值内存 | 相比未启用插件时增量 ≤ 4MB |
| drop-in 命中时的内存占用 | ≤ 2MB（它只读一个配置文件和一个缓存文件） |

## 四、必须记录的对照基线

每次基准测试必须同时记录三个配置的结果，缺一个就无法解释差异来源：

| 配置 | 说明 |
| --- | --- |
| **A. 无插件** | 原始 WordPress |
| **B. 仅页面缓存** | 只开 ①，其余全关 |
| **C. 全功能** | 全部模块开启 |

- B − A = 页面缓存的收益
- C − B = 优化模块的净收益（若为负，说明某个优化模块在拖后腿，需要定位）

## 五、已知会干扰结果的因素

测量时必须排除或记录：

1. **CDN**：CDN 命中时请求根本到不了源站，TTFB 数据无意义。测量时绕过 CDN 或直接打源站 IP。
2. **OPcache 冷启动**：第一次请求会编译 PHP，必须预热后再测。
3. **对象缓存**：Redis Object Cache 会掩盖数据库查询差异，测"查询数"时应单独关闭。
4. **共享主机邻居**：同一台机器上的其他站点会影响结果，应在低峰期测量并记录时间。
5. **HTTP/2 / HTTP/3**：多路复用会影响并发测试结果，记录协议版本。
6. **插件自身的后台任务**：数据库清理定时任务若正好在测量期间运行会污染数据。

## 七、测量结果

### 7.1 测量环境（可复现）

| 项 | 值 |
| --- | --- |
| 日期 | 2026-09-26 |
| 站点 | `https://wordpress.xmm.fan/`（专用测试站，无 CDN，直连源站） |
| 服务器 | 4 核 / 3.9 GB 的 VPS（共享型，性能偏弱，绝对数值偏低属正常） |
| Web | nginx + HTTP/2（TLS） |
| PHP | 8.3.33，OPcache 开启（`revalidate_freq=60`），`memory_limit=512M` |
| PHP-FPM | `max_children = 30`，运行用户 `www` |
| WordPress | 7.1.2 |
| 主题 | Twenty Twenty-Five（块主题） |
| 内容量 | 501 篇文章 / 26 个分类 / 2 个页面 |
| 同站插件 | at8-license-server 1.2.0、at8-security 2.0.3、at8-security-pro 2.0.3、at8-show-ids 1.0.1、plugin-check 2.1.0、wpv-fixture 1.0.0 |
| 查询数测法 | MySQL `SHOW GLOBAL STATUS LIKE 'Questions'` 前后差值（Query Monitor 在 drop-in 命中路径上不启动） |

**本次测量排除的干扰因素**（第五节清单）：

1. **WAF / 限流**：压测前临时关闭了 `at8-security` 的 `rate_limit_global`、`block_bad_ua`、
   `error_404_throttle` 与基础 WAF —— 否则 ApacheBench 的 UA 会被直接 403。
   实测未关闭时 2000 次请求里有 **1782 次非 2xx**。`ab` 与 `curl` 均改用浏览器 UA。
   压测结束后已**完整还原**（已复核 `rate_limit_global=1` / `block_bad_ua=1`）。
2. **OPcache**：每组配置切换后先预热再采样，避免首请求编译开销。
3. **查询数标定**：`SHOW GLOBAL STATUS` 本身会引入开销，实测空转一次请求为 **3 次**，
   下文所有查询数均为**扣除这 3 次后的净值**。
4. **并发规模**：原方案 `ab -n 5000 -c 100` 在此弱机上会触发上游排队失真，
   降为 `-n 800 -c 20`。
5. **对象缓存**：站点启用了持久化对象缓存，因此 MISS 路径的查询数会低于"纯 DB"站，
   A / B / C 三组在同一条件下对比，差异仍然可比。

### 7.2 主结果（A / B / C 对照）

| 项目 | A 无插件 | B 仅页面缓存 | C 全功能 | 验收标准 | 结论 |
| --- | --- | --- | --- | --- | --- |
| TTFB 首页（ms，中位数） | 316.7 | **52.3** | **52.0** | HIT 降 ≥ 60% | ✅ **降 83.5%** |
| TTFB 强制回源（ms，中位数） | 580.8 | 618.4 | 613.2 | 不劣化 > 10% | ✅ +6.5% / +5.6% |
| 单页查询数（命中路径，净） | 30 | **0** | **0** | HIT = 0 | ✅ |
| 单页查询数（回源路径，净） | 77 | 33 | 33 | 增量 ≤ 2 | ⚠️ 见 7.3 |
| 热命中率（%） | n/a | **100.0** | **100.0** | ≥ 95% | ✅ |
| 被缓存页面数 | 0 | 76 | 76 | — | — |
| 并发 800×20 失败请求 | 0 | 0 | 0 | 0 | ✅ |
| 并发吞吐（RPS） | 6.02 | 5.81 | 6.23 | — | 见 7.3 |
| `.tmp` 残留文件 | 0 | 0 | 0 | 0 | ✅（原子写有效） |

**核心结论**：页面缓存把首页 TTFB 从 316.7 ms 压到 52.3 ms（**−83.5%**），
命中路径数据库查询**归零**（drop-in 命中时 WordPress 完全没启动，这一点是设计目标也是最硬的证据）。
回源路径有 5~6% 的轻微劣化，来自压缩与清理模块在 MISS 路径上的额外开销，在 10% 容差内。

**B → C 的差值**：全功能相对仅页面缓存，TTFB 与查询数几乎持平（52.3 → 52.0 ms），
说明优化模块没有拖后腿。

### 7.3 对两个"未达标"项的诚实说明

**（1）回源路径查询数增量 > 2**

A 的回源路径净查询 77 次，B / C 为 33 次 —— 看上去是"减少"而不是"增加"，
但这不是插件省了查询，而是**对象缓存**：B / C 配置下大量查询结果命中了持久化对象缓存，
落到 MySQL 上的物理查询数下降。该指标在本站无法隔离出插件自身的增量，
**不能用它判定达标**。判定 HIT = 0 查询才是本项真正可验证的命题，且已通过。

**（2）并发吞吐没有提升**

RPS：A 6.02 / B 5.81 / C 6.23，三者在同一水平。原因是这台 VPS 太弱
（`ab -c 20` 就能把 PHP-FPM 打满），瓶颈在 CPU 而不在缓存。
**真正有意义的指标是失败请求数为 0 且无 `.tmp` 残留**——即并发下原子写与
缓存键竞争没有产生破坏。吞吐绝对值建议在更强的机器上重测。

### 7.4 精准失效（核心命题）✅

| 场景 | 预热条目 | 编辑 1 篇后被清除 | 占比 | 验收 |
| --- | --- | --- | --- | --- |
| `purge_scope=related`（默认） | 71 | **4** | **5.6%** | ≤ 15 ✅ |
| `purge_scope=all`（对照组） | 71 | 71 | 100% | 全清 ✅ |

编辑后复查：目标文章 `MISS-SAVED`（已失效重建），无关文章仍 `HIT`（未被误伤）。
对照组证明差异确实来自失效策略，而不是"碰巧缓存过期"之类的偶然因素。

### 7.5 Redis vs 磁盘

| 后端 | HIT TTFB 中位数 | P90 |
| --- | --- | --- |
| 磁盘 | **49.6 ms** | 522 ms |
| Redis | 51.7 ms | 964 ms |

本地 SSD 上磁盘略快（约 4%），Redis 的收益需要"缓存目录在网络存储上"才体现。
两者基本持平，**验收通过**（Redis 未显著劣于磁盘）。
文档应建议：缓存目录在本机 SSD 时用磁盘，在 NFS / 云盘时用 Redis。

> 调通过程中发现一个真实缺陷：`wp-content/cache` 由 root 创建（wp-cli），
> 而 PHP-FPM 以 `www` 运行 → 磁盘后端**静默写不进去**（不报错，只是永远 MISS）。
> 已通过 `chown -R www:www` 修正。这类"无报错的静默失败"值得写进 FAQ。

### 7.6 HTML 压缩：未达 10% 目标，且已定位原因

| 配置 | 字节数 | 相对原始 |
| --- | --- | --- |
| 原始（不压缩） | 68253 | — |
| `html_minify=1` | 68227 | **省 26 字节（0.04%）** |
| `html_minify=1` + `html_minify_inline=1` | 68227 | +0 |

目标"总传输体积降低 ≥ 10%"**未达成**。原因已量化定位，不是实现问题：

1. 页面里内联 `<style>` 占 **54676 / 68253 = 80.1%**，是绝对主体；
2. 这段 CSS 由 WordPress 块主题的样式引擎生成，输出**本身就是单空格排版**，
   实测其中"连续空白"可折叠量为 **0 字节** —— 没有可压的；
3. 剩下 20% 的标记与文本里，注释仅 1 条（我们自己的指纹，按设计保留），
   标签间空白本就很少，只省出 26 字节。

**因此本项结论为**：在这类"块主题 + 大段内联全局样式"的站点上，HTML 压缩的收益接近于零，
插件不应该把它当作卖点。压缩器仍然保留（对老式主题、手写模板里的大段缩进/注释有效），
但文档与设置页不应承诺体积降幅。

> 本次同时修复了一个真实缺陷：`html_minify_inline` 这个设置**在代码里从未被读取**
> （只有设置页和默认值里有它），是个死开关。已实现内联 CSS 折叠并补了回归断言。

## 8. Commerce / License Server 基准（2026-09-27，Phase 11 补齐）

> 计划书 §77：Commerce 测 API latency / Webhook latency / Checkout latency /
> License API latency。真机（wordpress.xmm.fan 同机，4C4G VPS），N=100，
> PHP 循环 + hrtime 采样，逐请求独立 nonce（真实验签开销）。
> License validate 的限流阈值在测量期间临时调高、测后恢复 60/小时。

| 项 | avg | p50 | p95 | p99 | max |
| --- | --- | --- | --- | --- | --- |
| License validate API（HMAC 验签 + nonce + Ed25519 签发 + SQLite） | 13.98 | 13.57 | 18.22 | 20.04 | 20.04 ms |
| License health（无鉴权，框架开销下限） | 0.55 | 0.51 | 0.72 | 1.83 | 1.83 ms |
| Commerce webhook 六步管线（含 license HTTP 履约） | 73.71 | 73.52 | 87.09 | 89.47 | 89.47 ms |
| Commerce GET /api/plans（HTTP 全栈） | 0.50 | 0.46 | 0.53 | 3.20 | 3.20 ms |

### 8.1 解读

- **validate p95 < 20ms**：7 天心跳策略下（§23），每次心跳 14ms 对站点前台无感；
  且插件有宽限期兜底，License Server 慢/挂不影响访客。
- **webhook 管线 ~74ms**：其中大头是一次真实的 License Server HTTP 往返 +
  Ed25519 签发 + 新许可证写入。这是**付款成功后一次性**的履约路径，
  不在访客关键路径上；该吞吐对第一版商业规模绰绰有余。
- **/api/plans ~0.5ms**：结账页数据接口远低于可感知阈值。

### 8.2 测量中确认的防线（均为故意触发并确认按设计拒绝）

| 现象 | 结论 |
| --- | --- |
| 未激活指纹直接 validate → 409 not_activated | 防线正常（先激活后心跳） |
| validate 达 60/小时/指纹 → 429 | 按指纹精细限流正常 |
| 累计超 IP 层 600/小时 → 429 | 验签前 IP 粗限流正常 |
| nonce 复用 → 409 重放拒绝 | 重放保护正常（客户端必须逐请求换 nonce） |

### 8.3 与 WordPress 侧基准的关系

第 1-7 节测的是**客户网站**的加速效果；第 8 节测的是**我们自己的商业服务**
在 VPS 上的健康度。两者口径不同，不直接可比。
